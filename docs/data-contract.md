# 流通追溯事件资料约定

## 分页与身份

`code` 与 `page` 定位分页来源；`event_id` 是事件身份。`event_time` 为业务时间，
`received_at` 是本地可见时间，两者分别留证、互不覆盖。`next` 只说明此响应仍有
续页，令牌原文冻结进分段游标，采集器不解释令牌内部结构。

## 留证字段（每个事件）

包装码（`code`）、批号（`batch`）、父子包装（`parent`）、企业节点（`node`，
来源缺省时留空，不凭空补造）、事件时间（`event_time`）、接收时间
（`received_at`）分别成列，并带内容指纹 `content_sha256` 与原文收据
`receipt_sha256`，可回指 `receipts` 表中的字节原文。

## 事件分类与批次语义

- 生产侧：`produce`、`pack` —— 只有这类事件建立“追溯码 → 批号”绑定；
- 退货：`return` —— 流通环节，之后去向未闭环前不推断下游；
- 拆包：`unpack` —— 流通环节，不产生新批次；流通再包装 `repack` 同样不属于生产；
- 其他流通：`inbound`、`outbound`、`ship`、`transfer`。

退货与拆包永远不会被误当成新批次生产；同一批号在生产侧出现不一致声明会进入待核。

## 分段收集与恢复

`segments` 表为每个码冻结查询范围（`scope_url`，保留 `code`）与当前游标
（`cursor` / `next_cursor`）。收集可在任意页中断，重开后按边界 URL 键控定位
冻结交互，已确认页面幂等跳过，只续跑边界之后的步骤。

## 缺口的两种状态（不得混同）

- `platform_pending`：分段尚未闭合，平台还有续页没有返回。这是“尚未看到”，
  不能当作链条完整；
- `review_pending`：原文已收到但存在问题——分页令牌失效（如 HTTP 410）、
  原文无法解析、同一分页号内容变化、同一 `event_id` 内容冲突。问题原文进入
  `quarantine` 表留证并报告待核范围，已确认事件保持不动，绝不推断下游全部去向。

## 夹具清单

- `normal.json`：同一码两页，退货事件业务时间早于包装、接收时间更晚；
- `conflict.json`：同一分页号返回不同内容（整页冲突）；
- `event-conflict.json`：不同分页重新声明同一 `event_id` 且内容不同（事件冲突）；
- `token-dead.json` / `token-recover.json`：续页令牌先 410 失效、新交互再恢复；
- `malformed.json`：来源正文不是合法 JSON；
- `multicode.json`：两个追溯码各自独立分段，含生产、出入库、退货、重新入库。

相同身份的版本冲突不再回滚原文：两份原文都保留，冲突方隔离待核；未闭合或有待核
记录的来源不能被解释成最终处置结果。
